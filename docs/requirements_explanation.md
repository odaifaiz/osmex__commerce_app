# شرح مستند المتطلبات: offline-support-system

## نظرة عامة

هذا المستند يحدد المتطلبات التقنية لنظام دعم العمل بدون اتصال (Offline-First) في تطبيق Flutter.

---

## مقدمة

**الهدف**: تمكين التطبيق من العمل بسلاسة أثناء انقطاع الشبكة.

**الطرق المستخدمة**:
- تخزين استجابات API محلياً
- العودة تلقائياً للبيانات المخزنة عند فشل الشبكة
- الكشف عن حالة الاتصال في الوقت الفعلي

---

## المصطلحات الأساسية

| المصطلح | الوصف |
|---------|-------|
| API_Client | طبقة التجريد لإنشاء طلبات HTTP |
| Cache_Manager | المكون الذي يتعامل مع التخزين المحلي |
| Connectivity_Service | خدمة مراقبة حالة الشبكة |
| Repository | طبقة التنسيق بين API و Cache |
| Cache_Entry | حاوية للبيانات المخزنة مع metadata |
| State_Notifier | مكون إدارة حالة UI باستخدام Riverpod |
| Resource_Key | معرف فريد للبيانات المخزنة |

---

## المتطلبات (15 متطلب)

### المتطلب 1: التخزين المؤقت عند نجاح API

**القصة**: يريد المطور تخزين استجابات API الناجحة تلقائياً.

**معايير القبول**:
1. عند نجاح طلب API (2xx) → تخزين البيانات مع Resource_Key
2. تخزين طابع времени вместе مع كل عنصر
3. تحديث الـ UI بالبيانات الجديدة
4. منع الكتابة المكررة
5. استخدام عمليات كتابة ذرية

---

### المتطلب 2: العودة تلقائياً للبيانات المخزنة

**القصة**: يريد المستخدم استمرار العمل أثناء انقطاع الشبكة.

**معايير القبول**:
1. عند فشل API → محاولة تحميل البيانات المخزنة
2. إرجاع البيانات المخزنة إذا كانت صالحة
3. تحديث حالة الـ UI لـ offline_mode
4. رمي CacheMissException إذا لم توجد بيانات مخزنة

---

### المتطلب 3: الكشف عن الاتصال في الوقت الفعلي

**القصة**: يريد المستخدم اكتشاف تغيرات حالة الشبكة تلقائياً.

**معايير القبول**:
1. مراقبة الاتصال باستخدام connectivity_plus
2. إرسال حدث online عند استعادة الاتصال
3. إرسال حدث offline عند فقدان الاتصال
4. تأخير (debounce) بـ 500ms لتجنب التذبذب

---

### المتطلب 4: التحقق من صحة التخزين

**القصة**: يريد المطور التحقق من سلامة البيانات المخزنة.

**معايير القبول**:
1. التحقق من صحة JSON قبل إرجاعه
2. حذف البيانات التالفة ورمي استثناء
3. دعم مدة صلاحية قابلة للتكوين (افتراضي 24 ساعة)
4. إرجاع metadata حول حالة البيانات (fresh/stale)

---

### المتطلب 5: نمط Repository

**القصة**: يريد المطور طبقة وصول بيانات مركزية ومنظمة.

**معايير القبول**:
1. توفير واجهة موحدة للوصول للبيانات
2. تحديد methods: getData, refreshData, clearCache, clearAllCache
3. تنفيذ منطق: محاولة API أولاً، ثم fallback للـ cache
4. دعم حقن التبعية (Dependency Injection)

---

### المتطلب 6: طبقة الخدمات

**القصة**: يريد المطور فصل واضح بين الطبقات.

**معايير القبول**:
1. IApiClient كواجهة مجردة
2. Cache_Manager كتنفيذ لـ ICacheManager
3. Connectivity_Service كـ singleton
4. APIs موثقة بوضوح
5. معالجة أخطاء صحيحة

---

### المتطلب 7: إدارة حالة UI

**القصة**: يريد المستخدم عرض حالة التطبيق بدقة.

**معايير القبول**:
1. أربع حالات: loading, loaded, error, offline_loaded
2. عرض indicator عند التحميل
3. عرض بيانات مع مؤشر online عند النجاح
4. عرض بيانات مع مؤشر offline عند استخدام Cache
5. عرض رسالة خطأ مع زر retry عند الفشل

---

### المتطلب 8: مؤشرات UI احترافية

**القصة**: يريد المستخدم تغذية بصرية واضحة عند العمل بدون اتصال.

**معايير القبول**:
1. شريط غير تداخلي في أعلى الشاشة (لون برتقالي)
2. نص: "Offline Mode - Showing cached data" + وقت التحديث
3. عدم منع التفاعل مع البيانات
4. اختفاء تلقائي مع snackbar عند استعادة الاتصال
5. ظهور خلال 500ms من فقدان الاتصال

---

### المتطلب 9: معالجة حالات الخطأ

**القصة**: يريد المستخدم رسائل خطأ واضحة وقابلة للتنفيذ.

**معايير القبول**:
1. عرض empty state عند عدم وجود إنترنت ولا cache
2. عرض "Request timed out" مع زر retry
3. عرض رسالة الخطأ من API أو رسالة عامة
4. محاولة تنظيف البيانات التالفة ثم retry
5. عدم ترك التطبيق في حالة غير متسقة

---

### المتطلب 10: معالجة الحالات الفارغة

**القصة**: يريد المستخدم تمييز واضح بين الفارغ والخطأ.

**معايير القبول**:
1. عرض "No data available" عند مصفوفة فارغة أو null
2. تمييز بصري عن حالة الخطأ
3. إمكانية إضافة زر refresh

---

### المتطلب 11: إلغاء التخزين والتحديث

**القصة**: يريد المستخدم تحديث البيانات تلقائياً.

**معايير القبول**:
1. إلغاء تلقائي للبيانات المنتهية الصلاحية
2. تجاهل Cache عند pull-to-refresh
3. دعم الإلغاء اليدوي
4. تحديث في الخلفية عند استعادة الاتصال
5. تنظيف البيانات القديمة عند بدء التطبيق

---

### المتطلب 12: أدوات إعادة الاستخدام

**القصة**: يريد المطور أدوات قابلة لإعادة الاستخدام.

**معايير القبول**:
1. دعم أي نوع بيانات عبر type parameter
2. توفير: serialize, deserialize, isValid
3. عدم ربط بمنتجات محددة
4. دعم multiple namespaces

---

### المتطلب 13: منطق آمن لإعادة المحاولة

**القصة**: يريد المطور عمليات إعادة آمنة.

**معايير القبول**:
1. تنفيذ exponential backoff (1s, 2s, 4s)
2. عدم إعادة كتابة البيانات غير المتغيرة
3. إمكانية إلغاء إعادة المحاولة
4. fallback للـ cache إذا فشلت جميع المحاولات

---

### المتطلب 14: وقت التحديث الأخير

**القصة**: يريد المستخدم معرفة وقت تحديث البيانات.

**معايير القبول**:
1. تخزين وقت التخزين بدقة
2. عرض الوقت بتنسيق مقروء ("منذ 5 دقائق")
3. تحديث الوقت عند_refresh من API
4. تحديث reactively

---

### المتطلب 15: سيناريوهات الأخطاء المتقدمة

**القصة**: يريد المطور معالجة الحالات الصعبة.

**معايير القبول**:
1. عرض Cache فوراً مع تحديث في الخلفية
2. تخزين الاستجابات الناجحة جزئياً
3. debounce لتغيرات الشبكة السريعة
4. عرض loading مع إمكانية الإلغاء
5. معاملة البيانات الفارغة كـ valid cache

---

## القرارات التقنية

### الحل المحلي: Hive

**الأسباب**:
- أداء أسرع من shared_preferences
- أمان الأنواع (Type Safety)
- دعم الكائنات المعقدة
- دعم null safety
- دعم التشفير
- بدون تبعيات native

### إدارة الحالة: Riverpod

**الأسباب**:
- أمان وقت التجميع
- سهولة الاختبار
- دعم async مدمج
- تكامل ممتاز مع Caching
- فصل واضح بين Definition و Consumption
